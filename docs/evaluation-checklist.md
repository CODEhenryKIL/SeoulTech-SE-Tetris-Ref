# 테트리스 요구사항 1·2 공통 평가 체크리스트

우리 팀 자체 점검과 다른 팀 상호 평가에 함께 사용하는 빈 양식이다. **팀마다 복사본 하나를 만들고, 평가한 실행 파일과 소스 버전을 고정해 기록한다.** 모든 판정은 미실행으로 시작한다. 이 양식에 적힌 확인 절차가 실제 검증을 완료했다는 뜻은 아니다.

기준: `TeamProject_Req1.pdf` 19쪽, `TeamProject_Req2.pdf` 12쪽. 쪽수는 표지를 포함한 PDF 페이지다. 작성 기준일: 2026-10-25. F·Q2·N·X 번호는 이 양식의 평가 ID이며 교수님 원문 번호나 우리 팀 칸반 카드 번호가 아니다. 교수님 추가 공지·e-class 답변이 있으면 해당 항목에 근거를 남겨 우선 적용한다.

### 판정과 증빙 작성법

- **통과**: 절차를 실행하거나 해당 버전의 재현 가능한 증빙을 확인했고 기대 결과와 일치.
- **부분**: 한 행에 포함된 일부 조건만 충족. 충족·미충족 조건을 메모에 분리.
- **실패**: 기대 결과와 다른 동작을 재현. 아래 결함 기록의 번호를 연결.
- **보류**: 실행 환경·재현 상태·자료가 없거나 기준 해석을 확인해야 함. 실패나 통과로 추정하지 않음.
- **해당없음**: 평가 범위 밖이거나 팀이 선택하지 않아도 되는 조건. 이유 필수. 필수 기능이 없다는 이유로 사용하지 않음.
- **미실행**: 아직 확인하지 않음. 빈 결과와 구분하기 위해 기본값으로 사용.

메모·증빙에는 `실행/코드/자동 테스트/팀 시연` 중 확인 방식, 화면·영상·로그·보고서 위치, 결함 번호를 적는다. 다른 commit의 테스트 결과만으로 현재 패키지를 통과 처리하지 않는다. 평가용 데이터로 실행하고, 저장 오류 시험은 백업한 별도 폴더에서 수행한다. 경계 보드를 일반 플레이로 만들기 어렵다면 대상 팀의 테스트 상태·재현 도구·시연을 요청하고 확인 방식을 기록한다.

이 문서는 교수님 배점표가 아니다. 항목 수나 통과율을 공식 점수로 바꾸지 않는다. X 항목은 예상 취약 동작을 구체화한 품질 검사이며, 별도의 새 기능을 요구하는 목록이 아니다.

### 공통 기준으로 강제하지 않을 것

- **지원 OS**: 요구사항 1은 Windows 11 또는 macOS 26 이상 중 하나를 허용한다(15·18쪽). 양쪽 지원을 선언했다면 선언 범위도 확인한다.
- **런타임**: Java 21 이상과 경로가 사전 설정되어 있다고 가정해도 된다. `JAVA_HOME`이 없는 PC에서 실행되지 않아도 된다는 허용이 있고, 런타임 포함도 선택 사항이다(1차 18쪽). 선언한 전제가 충족된 환경에서 더블클릭 실행을 확인한다.
- **커버리지**: 1차 17쪽은 `50-70% 이상` 표현이다. 2차 12쪽은 **중간 50%, 기말 70%**를 명시한다. 적용 단계·추가 공지를 기록하고 측정 분모·제외 근거를 확인한다. 우리 팀의 제품 전체 분모나 특정 도구를 강제하지 않는다.
- **속도**: Normal 대비 속도 증가량의 Easy 0.8배·Hard 1.2배가 기준이다. 타이머 간격을 단순히 ±20% 바꾸는 것과 다르다. 특정 레벨 상한·밀리초 수치·우리 팀 공식을 강제하지 않는다.
- **자체 아이템**: 기본 2종 외 최소 3종, 총 최소 5종이 기준이다. P/C/B라는 이름·효과, 300점, 5종 각 20%, 특정 대기열 구현은 공통 요구가 아니다.
- **무게추**: 너비 4칸과 접촉 후 좌우 이동 제한은 필수다. 그림의 세로 모양·문자·회전 여부는 고정하지 않는다. 효과 점수는 기본 0점이지만 적절한 팀 규칙으로 부여할 수 있다(2차 9쪽).
- **구현 도구**: 특정 IDE, Gradle, JUnit, JaCoCo, GitHub Actions, 특정 애니메이션 길이나 색상값은 공통 필수 도구·수치가 아니다. 2차의 Git/GitHub·Issue 관리 요구는 N 항목에서 별도로 확인한다.

## 4. 요구사항 2 추가 기능 · Q2 25항목

## 7. 실제 평가 순서

시간은 권장 운영 예시이며 공식 제한 시간이 아니다. 20~30분 핵심 점검만 했다면 다른 항목을 통과로 채우지 않는다.

1. **평가 준비**: 버전·환경·팀별 정책을 기록하고 자체 아이템 명세를 받는다.
2. **핵심 플레이**: N-01·04, F-01·02·03·09~17·27~32를 실제 조작한다.
3. **요구사항 2 핵심**: Q2-01·05~20 및 자체 3종을 확인한다. 10줄 경계·고정 상태는 필요한 경우 재현 도구를 사용한다.
4. **우선 경계 검사**: X-01·02·04~07·12~17을 먼저 실행한다. 나머지 X 항목과 설정·색각·화면 크기도 이어서 확인한다.
5. **자료 검증**: 분포 테스트·커버리지·비기능 검사·배포 재현·업무/Issue 이력을 확인한다.
6. **결과 정리**: 실패와 보류를 분리하고, 재현 절차·증빙·질문을 남긴다. 수정 후 같은 절차로 재검증한다.

## 10. 같은 기준으로 반복 사용하는 방법

1. 이 원본을 유지하고 `평가대상팀-평가일-버전` 이름으로 복사한다.
2. 우리 팀에서는 `chore/req2-final-verification`의 최종 평가 버전을, 다른 팀에서는 그 팀의 제출 패키지·commit을 기록한다.
3. 대상 팀 정책과 자체 아이템 명세를 먼저 채운다. 모든 결과는 미실행에서 시작한다.
4. 확인한 행만 판정을 바꾸고 증빙·결함 ID를 연결한다. 자동 검사와 실제 키/배포물 확인을 구분한다.
5. 수정 버전을 재검증할 때 기존 결과를 지우지 말고 결함 블록에 수정 버전·재검증 결과를 추가한다. 평가 버전이 크게 달라지면 새 복사본을 만든다.
